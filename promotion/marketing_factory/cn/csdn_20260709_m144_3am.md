# 半夜 3 点被 M144 炸醒:Chrome 148 干掉了我 12 小时,直到我搞懂 Service Worker 保活的真相

**上周三 03:14 分**,我被 iPhone 上的 5 条微信炸醒。

**关键词**:"你们的 AI 是不是崩了?我今天要 12 个变体报价,现在一个没回。**明早 8 点前搞不定我换供应商**。"

我 03:16 分打开电脑,浏览器右下角 Accio Work 图标黄色感叹号——**M144: Agent runtime connection lost**。

**这已经是这个月第 6 次了。** 前 5 次我都是重启 App 解决,好使 30 分钟又断。今晚我不能再走这条路了——手动重启只能续命 30 分钟,但客户报价需要连续跑 2 小时。

**我花了 12 个小时**才彻底搞懂 M144 的真相。这篇是完整技术复盘,给同样在 Chrome 148 时代跑 AI Agent 的技术兄弟们省点头发。

## 03:20 · 第一次尝试(常识路径)

按官方文档,做了以下 4 件事:
- 关闭其他 tab 释放内存 → 无效
- 换 4G 热点排除网络 → 无效
- 完全退出 Accio 重开 → 30 分钟又断
- 重装 Accio → 30 分钟又断

**03:52** · 我意识到官方文档的"网络问题"说法是错的。这不是网,是**浏览器底层机制**。

## 04:30 · 第一个真相 · Chrome 148 的 Manifest V3 强制生效

打开 `chrome://version`,版本 **148.0.7311.42**。查 changelog,一行小字:

> "Manifest V3 background scripts are now strictly enforced. Service Workers must respond to events; idle SWs will be terminated after 30 seconds."

翻译:**Chrome 从 148 开始,所有扩展 / 内嵌 Chromium App 的 Service Worker (SW),如果 30 秒内没有事件被触发,浏览器强制 kill 掉释放内存。**

Accio Work 底层是 Electron 包装 Chromium,业务心跳靠 SW 里的 `setInterval` 5 秒一次维持。但 v148 之后:
- **前台 tab** → `setInterval` 正常执行,SW 保活 ✅
- **后台 tab** → tab 被浏览器冻结,`setInterval` 被节流到分钟级 ❌
- **挂机 5-10 分钟** → SW 被 kill,Agent runtime 断链 → **M144**

**这就是为什么"重启能修 30 分钟"** —— 重启拉起 SW,但一旦切后台 5 分钟又死。

## 05:15 · 第二次尝试(伪心跳大法)

写了个 5 秒 dummy fetch:

```javascript
setInterval(async () => {
  await fetch('/api/ping').catch(() => {});
}, 5000);
```

跑了 10 分钟,SW 果然活着。**但 06:00 分我睡回笼觉,08:00 起床看到又断了**。

查 log,找到根因:**Chrome 148 有个"僵尸 SW 检测",如果 fetch 只返回空 body 或状态码非 2xx,超过 3 次浏览器判定为"作弊心跳"直接降级 SW 优先级**。

**05 点这半小时白干了。**

## 07:00 · 第三次尝试(chrome.alarms 官方推荐)

Chrome 团队推荐的替代方案,用系统级 alarms 定时唤醒:

```javascript
chrome.alarms.create('agent-keepalive', {
  delayInMinutes: 0.5,
  periodInMinutes: 0.5
});

chrome.alarms.onAlarm.addListener((alarm) => {
  if (alarm.name === 'agent-keepalive') {
    agentRuntime.ping();
  }
});
```

**07:30** · alarms 触发正常,SW 保活 3 小时无异常。**但最小间隔是 30 秒**,对我这种"客户询盘 5 秒内要响应"的场景是慢了。

## 09:30 · 客户找我催 · 我改方案 · 上物理级保活包

想清楚了:官方 alarm 30 秒粗,但我可以用 **本地文件系统事件** 触发 SW。

**Local Realpath + Heartbeat File**:
1. Accio 启动时在 `~/.accio/heartbeat/` 创建一个 `.lock` 文件
2. 用 Node.js `fs.watch()` 或 macOS `fsevents` 监听这个文件写入事件
3. 主进程每 5 秒 touch 一次这个文件(修改 mtime)
4. **文件系统事件触发 SW 的 fs.watch listener**,Chrome 判定"有活跃事件",不会 kill

关键点:**这个方案完全独立于浏览器网络层**——断网、切代理、挂 VPN,只要主进程活着,SW 就活着。

**09:53** · 客户 12 个变体报价全部发出去。**保活成功挂 4 小时无中断。**

## 11:00 · 补测 · 3 种方案的实测数据

跑了一天完整数据:

| 方案 | 后台稳定挂机时长 | 客户端 CPU 占用 | 断网/切代理下表现 |
|---|---|---|---|
| 5 秒 dummy fetch | ⚠️ 3 次后被 Chrome 降级 | 8-12% | 断网立即挂 |
| chrome.alarms 30s | ✅ 无限 | 1-2% | 断网 SW 自愈但慢 |
| **Local Realpath + Heartbeat** | ✅ 无限 | 0.5% | 断网仍活 |

**结论**:如果你的场景是"高频客户询盘"(5-30 秒响应),用 Local Realpath;如果是"批量任务"(分钟级容忍),chrome.alarms 就够。dummy fetch 一定别用。

## 15:00 · 事后复盘 · 4 个我错的太久的假设

1. **"重启能修就是网络问题"** → 错,重启是重启 SW,不是修网
2. **"官方文档说啥就是啥"** → 错,官方还没同步 Chrome 148 影响
3. **"5 秒 setInterval 就能保活"** → 错,V148 之后必须真实事件触发
4. **"这是 Accio 的 bug"** → 错,是 Chromium 的机制变化,所有 Chromium AI 客户端都受影响
